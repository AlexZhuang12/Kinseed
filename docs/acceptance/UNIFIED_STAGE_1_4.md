# 1.4本地整合 staging 驗收

整合版本1.4.0-local.1；正式控制器仍未更新。此記錄接續工具獨立候選的歷史驗收，不把舊候選的包雜湊或測試版本當成本次來源。

本次由AI執行，使用三個synthetic合成個體、明示合成記憶／用量及舊報告；工具計算、SQLite、HTTP、Chrome及npm子程序為真實執行，沒有真實LLM呼叫或外部寄送。不冒稱模型自然行為或人類驗收。

## 已驗證

- 完整Node回歸614項通過，包含原606項與8項staging邊界檢查，定向子集不重複加總。
- 原有四語操作／工具／首次設定回歸215項通過；新增整合四語檢查33項通過，合計248項UI檢查。
- 三個合成個體、工具成果、日報及封存管理在同一後端；API、頁面標題、頁首與套件對齊1.4.0-local.1，staging頁明示STAGING。
- 原版來源建立舊資料，整合來源開啟相同runtime；身份、出生、記憶、歷史前綴、原權限、每日時間與截止、已用輪數及網路用量保留；新權限預設關閉。
- 合成runner使用實際工具建立JavaScript作品，真實算得2+3=5並經commit_cycle保存明示合成的新記憶；不是LLM產出。
- 原版來源回退讀取同一份較新DB，保留新記憶、新工具表、新歷史、已用輪數及流量；再升級可讀作品與材料。沒有用舊DB覆蓋新DB。
- 冷備份逐檔位元比對一致；重啟取消每日安排，不自動恢復、重生或清零。
- npm啟動、狀態、停止、關閉與重複啟動已用真實子程序測試；staging只用自己的資料、獨立埠與singleton，拒絕正式／外來會話、無標記及非合成registry資料。
- staging模型、諮詢、委派與自動日報停用；驗收結束服務關閉、合成個體停止、新工具權限全部關閉，未匯入OAuth或正式資料。

## 實際診斷與修正

舊工作台把工程驗證環境的日報按鈕一律改成封鎖提示，即使該後端已有獨立日報。現只對沒有整合日報的工程台保留封鎖；具備同一後端local_unification標記者沿既有相對路徑開啟，沒有恢復外部正式報告網址。

首次介面測試曾未展開收合導航、又在非同步選項尚未載入時計數，已改成實際操作順序與選定對象後核對；原失敗保留。首輪合成記憶種子缺少對應A投影事件而被完整性檢查擋下，修正的是測試種子的證據，不是放寬Store驗證或修補正式記憶。

新staging未繼承.private，因此首次OCR驗收因缺少語言檔而如實失敗。只補入兩個固定名稱／大小／SHA的公開OCR語言資產，沒有複製私人設定、身份或LLM模型；文件與OCR重驗通過。正式切換前須另做受控資產準備及tools:check，不能只更新npm鎖檔就宣稱所有工具可用。

## 界線

不是正式部署。舊版回退使用隔離參數啟動原版核心；沒有執行會使用正式埠的舊CLI，亦沒有演練宿主機突然斷電。沒有第三方全面人類驗收、母語審閱或第二台Windows驗收。原生Office及長期正式負載等既有限制仍保留。

Gmail真實結果沿用先前Owner批准測試信及Owner收件確認，本次沒有複製該連線或再次寄信。正式切換仍需另外授權，部署時不搬合成DB、.private、測試報告或staging標記；重啟後的每日生活恢復範圍及新增工具權限另由Owner決定。
